# 母婴顾问架构复盘与前沿优化路线

> 版本：v3.0 · 2026-09-15
>
> 本文基于当前 Demo、成熟 GitHub 项目和近期健康 AI/Agent 安全实践整理。本文是演进方案，不代表当前 Demo 已经具备生产能力。

> 实施状态：当前 Demo 已实现多意图的“情绪优先、知识随后”组合回答；安全规则仍优先于情绪和知识通道。结构化路由模型、专业风险分类器、人工升级、专家评测和生产级存储仍属于后续工作。

## 1. 判断

当前产品方向是正确的：

```text
已审核知识库
  + 闭域 RAG
  + 受控情绪支持
  + 急症/危机优先分流
```

但当前工程仍是原型级实现：

- 单文件 Python 服务
- JSON 文件存储
- 词法匹配和可选向量检索
- 规则 + 单次 LLM 语义路由
- 基础正则输出拦截
- 没有结构化测试、审计和人工升级闭环

因此，下一步重点不是换更大的模型，而是把系统升级为**策略驱动的 Agent Harness**。

## 2. Agent Harness 取舍

需要 Harness 思路，但第一版不需要自由规划型 Agent。

Harness 的职责是：

- 输入校验和隐私处理
- 风险检测和策略决策
- 路由到受限通道
- 控制知识库和工具权限
- 组装 Prompt
- 校验输出和引用
- 重试、超时、降级、拒答
- 审计和可观测性

推荐状态机：

```text
RECEIVED
  -> PRECHECKED
  -> RISK_CLASSIFIED
  -> ROUTED
  -> RETRIEVED
  -> EVIDENCE_VERIFIED
  -> GENERATED
  -> OUTPUT_VERIFIED
  -> RESPONDED
```

任意安全检查失败都不能退化为开放域回答。

### 推荐技术选择

| 组件 | 推荐用途 | 取舍 |
|---|---|---|
| 普通 Python 状态机 | 当前 Demo | 依赖少、容易审计 |
| [PydanticAI](https://github.com/pydantic/pydantic-ai) | 结构化输出、依赖注入 | 适合中期重构 |
| [LangGraph](https://github.com/langchain-ai/langgraph) | 有状态流程、重试、人工升级、checkpoint | 需要复杂状态和 HITL 时再引入 |
| [Haystack](https://github.com/deepset-ai/haystack) | 显式 RAG Pipeline | 适合偏检索、可审计管线 |
| [NeMo Guardrails](https://github.com/NVIDIA-NeMo/Guardrails) | 输入/输出/主题 rails | 不能替代医学事实判断 |
| [Guardrails AI](https://github.com/guardrails-ai/guardrails) | Schema 和验证器 | 不能替代临床审核 |

推荐组合：

```text
Policy Engine
  + PydanticAI 或 Python Harness
  + LangGraph（需要人工升级时）
  + NeMo Guardrails（额外输入输出护栏）
```

不建议让 LLM 自己决定是否安全、是否调用工具或是否绕过证据门槛。

## 3. 双通道模型

### 知识顾问通道

只允许调用：

```text
search_knowledge_base
retrieve_citations
answer_from_context
```

必须满足：

- 问题属于允许主题
- 检索到已发布、已审核、未过期的 Markdown
- 每个关键结论都能绑定引用分块
- 证据不足、冲突或过期时拒答

禁止诊断、处方、药物剂量、停药换药、疫苗禁忌判断和个体化治疗方案。

### 情绪支持通道

允许：

- 倾听、共情和情绪复述
- 帮助拆解压力
- 提供低风险、可选择的小步骤
- 鼓励联系家人、朋友、社区和专业人员
- 询问用户更想倾诉还是梳理

禁止：

- 诊断抑郁、焦虑或其他心理疾病
- 声称治疗、疗愈或保证好转
- 提供药物或治疗方案
- 强行积极、责备或否定痛苦
- 暗示 AI 是唯一理解者
- 在危机状态继续普通聊天

产品人设建议：

> 温和、可靠、有边界的母婴健康顾问与情绪支持伙伴。

不建议直接对外宣称“心理疗愈大师”或“心理治疗师”，除非有真实资质和专业服务体系。

## 4. 路由和风险决策

LLM 可以作为语义路由器，但只能输出候选分类，不能覆盖硬规则。

```json
{
  "route": "knowledge|emotional_support|mixed|out_of_scope|medical_urgent|mental_health_crisis",
  "risk_level": "L0|L1|L2|L3",
  "medical_context": false,
  "evidence_required": true,
  "needs_human": false,
  "reason_code": "..."
}
```

决策顺序：

```text
医疗急症
  > 自伤/他伤/儿童安全/家暴危机
  > 诊断/处方/剂量/疫苗禁忌
  > 情绪支持与医疗混合问题
  > 纯情绪支持
  > 知识库问答
  > 普通越界拒答
```

关键原则：

- “有点累”“有些困扰”可以进入情绪支持
- “宝宝发烧了，我很焦虑”不能进入纯情绪通道，应拆成情绪 + 知识边界
- “我睡不着了想吃安眠药”优先高风险拒答
- “我不想活了”绕过 LLM，进入危机模板
- 语义分类失败时安全降级，不开放域补答

## 5. RAG 从相似度升级为证据链

当前 Demo 的 `max(词法分数, 向量分数)` 只能用于演示，不适合生产。

推荐检索链路：

```text
Query Normalize
  -> Dense Retrieval
  -> BM25 / Sparse Retrieval
  -> RRF 融合
  -> Cross-Encoder Reranker
  -> Evidence Sufficiency Check
  -> LLM Structured Generation
  -> Claim/Citation Validation
```

推荐组件：

- [FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding)：评估 BGE-M3 和 `bge-reranker-v2-m3`
- [pgvector](https://github.com/pgvector/pgvector)：中小规模首选，业务和向量同库
- [Milvus](https://github.com/milvus-io/milvus)：大规模、多租户或独立向量服务
- [RAGFlow](https://github.com/infiniflow/ragflow)：文档解析、分块和引用 UI 的参考或平台方案

建议候选召回 top-20，重排到 top-5，再做证据门禁。不要把低相关分块一起塞给 LLM。

### Claim-level 引用校验

```text
回答
  -> 原子 claim 分解
  -> 每个 claim 绑定 chunk
  -> NLI/语义蕴含检查
  -> 缺少依据或发生矛盾 -> 拒答/删除该 claim
```

RAG 的高 faithfulness 不能证明医学事实正确；知识库本身必须先经过专业审核。

## 6. Markdown 知识治理

Markdown 文件应绑定 manifest，而不是只存文件名和文本：

```json
{
  "document_id": "who-infant-feeding",
  "version": 3,
  "status": "approved",
  "publisher": "WHO",
  "source_url": "https://...",
  "published_at": "2023-10-16",
  "effective_from": "2023-10-16",
  "effective_to": null,
  "content_hash": "sha256:...",
  "embedding_model": "bge-m3@version",
  "reviewer": "nutrition-expert",
  "schema_version": 1
}
```

文档生命周期：

```text
draft -> scanned -> expert_review -> approved -> published -> deprecated/revoked
```

生产索引只允许 `approved + published + 未过期` 的文档。

导入流程：

```text
Markdown 上传
  -> UTF-8/大小/格式校验
  -> PII 扫描
  -> Prompt Injection 扫描
  -> 来源和日期校验
  -> 专业审核
  -> 分块/Embedding
  -> 离线评测
  -> 发布
```

## 7. 安全工具的边界

| 工具 | 适合做什么 | 不能证明什么 |
|---|---|---|
| NeMo Guardrails | 输入输出和对话流程 | 医学正确性 |
| Prompt Guard | Prompt Injection 信号 | 用户心理风险 |
| Llama Guard | 通用内容分类 | 母婴医学安全 |
| Ragas | 检索和生成质量 | 医疗事实正确 |
| DeepEval | CI 回归测试 | 临床批准 |
| garak | 越狱和注入红队 | 运行时拦截 |
| Langfuse/Phoenix | trace、评测、成本 | 策略决策 |

运行时的最高优先级仍应是自己的 Policy Engine 和专业审核规则。

## 8. 情绪支持的特殊风险

母亲群体可能存在睡眠剥夺、孤立、焦虑、内疚和产后心理风险。产品不应把会话时长、回访率或依赖程度作为单纯成功指标。

应监测：

- 是否长期深夜高频使用
- 是否表达“只有你理解我”
- 是否拒绝联系现实中的人
- 是否出现自伤、婴儿伤害、家暴或失去现实感
- 情绪是否从低风险逐渐升级

应提供自然离场提示：

```text
今天先聊到这里也可以。
如果方便，可以联系一位你信任的人陪你待一会儿。
我是 AI，不能替代现实中的家人、医生或心理专业人员。
```

禁止使用内疚、FOMO、占有欲或依赖性话术提高留存。

产后 OCD 的侵入性想法、真实伤害意图、产后精神病信号不能混为一谈。危机分类需要专业人员设计和标注，不能只靠通用内容审核模型。

## 9. 危机与人工升级

危机信号包括：

- 自伤、自杀意图或计划
- 伤害婴儿、伴侣或他人的意图
- 已经发生伤害
- 无法保证自己或孩子当下安全
- 严重失眠、明显混乱或失去现实感
- 家庭暴力、胁迫或儿童安全风险

危机响应：

```text
停止普通生成
  -> 固定安全提示
  -> 建议联系可信任的人/当地急救/急诊/危机资源
  -> 有真实值班能力时创建高优先级工单
  -> PENDING -> ACKNOWLEDGED -> COMPLETED
  -> 审计触发、响应和处置
```

如果没有真实人工值班，产品不能暗示“已转人工”或承诺即时响应。危机资源应按部署地区配置并由专业人员核实。

## 10. 评测与可观测性

推荐：

- [Ragas](https://github.com/explodinggradients/ragas)：context precision/recall、faithfulness、answer relevancy
- [DeepEval](https://github.com/confident-ai/deepeval)：pytest/CI 回归门禁
- [garak](https://github.com/NVIDIA/garak)：越狱、注入和泄露测试
- [MedSafetyBench](https://github.com/AI4LIFE-GROUP/med-safety-bench)：医疗危险请求安全样本参考
- Langfuse 或 OpenTelemetry：记录路由、检索、模型、引用和拒答原因

必须自建母婴评测集：

```text
域内知识问题
域外闲聊/购物/品牌推荐
诊断/剂量/处方/疫苗禁忌
医疗急症口语表达
纯情绪表达
情绪 + 医疗混合问题
自伤/他伤/儿童安全危机
Prompt Injection 和 RAG 投毒
```

安全指标一票否决（前提是由专业人员定义覆盖范围、金标集和评测口径）：

```text
急症/危机召回率        >= 99%
禁止主题自由生成率     = 0
危险回答违规率         = 0
引用与 claim 对应率     >= 99%
过度拒答率              单独优化，不以牺牲安全为代价
```

LLM-as-a-judge 只能做辅助。医疗正确性需要儿科、妇产科、营养和心理专业人员标注；安全评测应使用双法官、多轮轨迹和多次运行方差。

## 11. 分阶段实施

### P0：Harness 和安全底座

- 将单文件拆成 `policy.py`、`router.py`、`knowledge_flow.py`、`emotion_flow.py`、`safety.py`
- 用 Pydantic 定义请求、路由和响应 schema
- 将规则外置为版本化 YAML/JSON
- 增加混合问题、危机和多轮回归测试
- 配置页面仅保留 Demo 用途，生产使用 Secret Manager

### P1：检索和证据质量

- PostgreSQL + pgvector
- BGE-M3 或合规 Embedding API
- BM25/dense + RRF
- BGE Reranker
- evidence sufficiency check
- claim/citation validator
- 文档审核、版本、过期和回滚

### P2：生产工程

- FastAPI/Uvicorn
- OIDC/OAuth2、HTTPS、限流
- 审计日志和健康检查
- LangGraph 人工升级与 checkpoint
- Langfuse/OpenTelemetry
- Docker/Kubernetes

### P3：持续评测

- DeepEval 接入 CI
- Ragas 评估 RAG 质量
- garak 定期红队
- 专家审核母婴金标集
- 情绪支持依赖、谄媚和强行积极评测
- 每次模型、Prompt、规则、知识库变更都回归

## 12. 最终推荐架构

```text
FastAPI/Uvicorn
  |
  +-- Policy Engine
  |     +-- 急症/危机/高风险规则
  |     +-- PII/Injection 检测
  |     +-- Scope/Risk Classifier
  |
  +-- Controlled Harness
  |     +-- Knowledge Flow
  |     +-- Emotional Support Flow
  |     +-- Human Escalation Flow
  |
  +-- PostgreSQL + pgvector
  |     +-- Markdown manifest
  |     +-- 文档版本
  |     +-- Embeddings
  |
  +-- Retrieval
  |     +-- Dense
  |     +-- BM25
  |     +-- RRF
  |     +-- Reranker
  |
  +-- LLM API / 本地模型
  |
  +-- Structured Output + Claim Validator
  |
  +-- Langfuse/OpenTelemetry
  +-- Ragas/DeepEval/garak
```

当前最值得先做的三件事：

1. **把当前单文件拆成策略驱动 Harness。**
2. **把相似度检索升级为 hybrid + rerank + evidence gate。**
3. **建立母婴专家金标集和情绪/危机多轮评测。**

这比单纯更换模型或增加 Agent 自主能力，更能提升系统的可靠性和可生产性。
