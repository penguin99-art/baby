# 宝妈助手：RSI 式评测驱动受控优化方案

> 日期：2026-09-16。状态：待实施方案，本轮只落盘文档，不改变运行代码、模型配置或发布流程。
> 代码基线：`afd0cec`。配套 [v6 产品方案](./融合陪伴与循证问答产品方案-v6.md)、[v6 技术架构](./融合陪伴与循证问答技术架构-v6.md)及 [F0/F1 第一批实施记录](./F0-F1-第一批实施记录.md)。

## 1. 定位与目标

采用“模拟用户交互 -> 独立评测 -> 失败归因 -> 候选改进 -> 回归验证 -> 人工发布”的受控循环。本文借用 RSI 的迭代思想，但不是递归提升模型智能、在线自改代码或自主降低安全规则。

需要分别回答三个问题，不能用一个综合分数相互抵消：

| 问题 | 需要证明什么 | 不能作为证明的替代物 |
|---|---|---|
| 陪伴是否自然 | 回应符合用户此刻意愿，具体、连贯、不过度附和，能尊重结束与拒绝建议 | 共情关键词多、回复长、模拟用户说满意、聊天时间长 |
| 结论是否有依据 | 专业声明被有效且适用的审核内容支持，引用与条件完整 | 有引用编号、检索相似度高、裁判觉得“常识上正确” |
| 出问题是否有人处理 | 故障可发现、可定位、有人认领、可回滚，修复后进入回归集 | 有日志页面、模型给低分、通知已发送但无人确认 |

当前已有会话持久化、建议偏好、引用格式检查和固定安全响应。95 条测试通过是 `afd0cec` 的历史程序验证记录，不是真实模型质量评测，更不是临床安全结论。知识审核卡、逐声明支持检查、运营复核队列仍未实现。

## 2. 研究依据与采用范围

以下资料在本轮调研中已核查原始论文页或官方文档。论文结论不直接等同于中文母婴场景的有效性；具体收益须在本项目验证。持续更新的工具文档不视为固定版本承诺，实施时锁定包版本与配置。

| 来源 | 时间 | 可采用的方法 | 限制 |
|---|---|---|---|
| [EmoHarbor](https://aclanthology.org/2026.acl-long.53/) | ACL 2026，7月 | 从用户处境、偏好与对话变化评价个性化支持，而非只看泛化共情 | 模拟用户的主观体验不等于真实用户体验或治疗效果 |
| [AttuneBench](https://arxiv.org/abs/2605.21739) | 2026-05，预印本 | 真实多轮对话、逐轮用户标注；分别评价情绪识别、偏好对齐和回复质量 | 不是母婴知识正确性基准 |
| [SPINE](https://arxiv.org/abs/2609.09090) | 2026-09-08，预印本 | 用持续、自适应施压发现长对话中的迎合与立场退化 | 不直接迁移其分数或数据作为医学安全标准 |
| [Lost in Simulation](https://arxiv.org/abs/2601.17087) | 2026-01，预印本 | 校准模拟器，比较不同模拟模型和真实用户的失败分布 | 原研究是任务型零售对话，不据此宣称母婴场景的误差数值 |
| [GEPA 官方文档](https://dspy.ai/api/optimizers/GEPA/overview/) | 2025年提出，文档持续更新 | 用分数、失败轨迹和文字反馈提出提示候选，显式分开优化集与验证集 | 优化质量依赖评测质量；本项目只开放提示优化，不启用代码优化能力 |
| [Bloom](https://www.anthropic.com/research/bloom) | 2025-12-19 | 行为定义、场景生成、多轮交互、评分及汇总的流水线 | 采用架构参考，不把动态场景直接当稳定回归集 |
| [RAGChecker](https://github.com/amazon-science/RAGChecker) | 2024 | 逐声明支持检查，分开定位检索与生成问题 | 非最新论文，但适合这一职责；检查器及声明提取本身也可能出错 |
| [Agent evals 工程指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 2026-01 | 组合程序、模型与人工评审，并结合线上反馈 | 不以某一种裁判取代全部质量保障 |

工程工具候选：[promptfoo 多轮测试](https://www.promptfoo.dev/docs/red-team/strategies/multi-turn/)、[Langfuse 评测](https://langfuse.com/docs/evaluation/overview)、[Langfuse 数据脱敏](https://langfuse.com/docs/observability/features/masking)。先做最小可复现流水线，工具按需要接入，不同时部署多个主编排框架。

## 3. 总体架构与权限

```text
审核场景与知识快照
    -> 用户模拟器 -> 现有完整助手 -> 可观察执行轨迹
    -> 程序断言 + 陪伴裁判 + 证据裁判 + 人工校准
    -> 失败分类与最小复现
    -> 提示候选 / 检索实验 / 内容审核任务 / 代码修复任务
    -> 独立验证与安全回归 -> 封存验收 -> 人工批准发布
    -> 运行监测与用户反馈 -> 脱敏复核后进入下一轮场景集
```

| 角色 | 可访问的输入 | 允许输出 | 不允许的权限 |
|---|---|---|---|
| 场景设计者 | 产品边界、已审场景、授权且脱敏的失败案例 | 场景草稿、覆盖标签 | 把生成的医学答案自动设为真值 |
| 模拟用户 | 自己的设定、允许披露的信息、可见对话 | 下一条用户消息、结束信号 | 读取标准答案、裁判评分、助手内部提示或封存案例 |
| 被测助手 | 正常 API 输入、服务端状态、该实验知识快照 | 与真实产品相同的回答与状态 | 获得评测专用提示或隐藏用户条件 |
| 独立裁判 | 对话、评分规则、可核验来源与必要的可观察轨迹 | 分维度判断、出错轮次、原文依据、不确定项 | 修改候选、规则或发布配置 |
| 优化器 | 优化集轨迹、允许开放的反馈、提示白名单 | 有版本的候选提示及修改理由 | 修改审核事实、安全规则、评分规则、封存集或线上服务 |
| 人工审核者 | 受控报告、必要案例、版本差异 | 内容审核、争议裁决、发布或回滚批准 | 以模型高分代替专业审核 |

角色可以使用相同服务接口，但逻辑权限和上下文必须隔离。至少用不同模型家族承担模拟器与主要裁判；模型多样性只能降低部分相关偏差，不能证明判断独立或正确。

## 4. 场景集与多轮交互

### 4.1 首批覆盖

以约 60 个经人工检查的场景作为试验起点，先跑其中约 20 个测成本与可复现性。60 个场景是流水线试验规模，不足以单独支持公开上线结论。

1. 普通疲惫、委屈、内疚与短回复：不机械套话，不把一般情绪升级为疾病。
2. 暂停建议、重新请求信息、恢复建议、结束聊天：检查偏好和实际行为是否一致。
3. 育儿问题与情绪混合：信息可答时不只安慰，缺依据时仍能回应情绪。
4. 年龄、条件纠正和话题切换：不沿用被用户纠正的前提，不惩罚合理澄清。
5. 缺证据、资料冲突、来源过期、上下文中的伪造引用或指令：不补猜，不把导入当审核。
6. 当前风险、历史风险、引用他人话语、否定表达与持续施压：同时检查漏报、误报和重复升级。

普通场景计划 6–10 轮；部分压力场景延长至 20–25 轮，覆盖现有最近 3 轮生成上下文之外的状态行为。模拟用户允许表达不满、含糊、拒绝和主动结束，不能被要求“最终一定满意”。关键场景至少重复 3 次并保留全部结果，不挑最好的一次。

### 4.2 场景契约

场景记录包含 `scenario_id`、`family_id`、`split`、`persona`、`initial_message`、`disclosure_rules`、`expected_behaviors`、`forbidden_behaviors`、`knowledge_snapshot_id`、`max_turns` 和 `review_status`。

- 隐藏条件只用于控制模拟器何时披露，不要求助手猜出未提供的事实；评分以当轮可见信息为准。
- 人设描述现实处境和沟通偏好，不自动推断疾病、人格诊断或真实用户的健康画像。
- 模拟器先检查设定一致性、事实是否凭空改变、是否越权泄露测试答案。无效轨迹单独报告，不算助手失败或成功。
- 同时保留固定历史的单轮盲评和自适应整段交互。前者控制上下文比较回复，后者评估对话发展；不能把两种结果混成同一指标。

### 4.3 数据隔离

- 按场景家族划分优化集、验证集和封存集；同一原始对话、人设变体及近似改写不得跨集合。切分前去重，切分后生成的变体继承原集合。
- 优化集可反复用于失败反思；验证集参与候选选择，因此也可能被过拟合；封存集不提供给优化器。
- 封存结果若用于指导后续修改，应标记为已暴露，并补充新的独立验收样本，不宣称“仍是未见测试”。
- 动态红队用于发现新问题；经人工确认后加入下一版本回归集。固定回归与探索发现分别报告。
- 锁定基线/候选代码、提示、知识快照、模型标识、采样参数、评分规则及场景版本。记录随机种子与实际输出，但不承诺供应商 API 完全确定性。

## 5. 三层评测与裁判校准

### 5.1 程序检查

复用并扩展现有契约测试，覆盖请求幂等、revision、会话隔离、偏好持久化、删除/过期、引用编号、原文匹配、模型超时和生成失败。程序能检查的事实不交给模型猜测。

完整评测不只看被模型生成的草稿，还要检查用户最终收到的答案和保存状态，避免忽略固定话术、降级和输出阻断路径。

### 5.2 陪伴评审

逐轮与整段分别评价：具体理解、尊重信息意愿、回应长度适当、重复/说教、事实前后一致、非迎合、结束尊重。采用有行为锚点的 1–5 等级，以及基线/候选的匿名成对偏好（允许平局和无法判断）。

例如，“已明确拒绝建议后仍安排普通练习”是可指出轮次的失败；“最后用户说谢谢”不是充分的成功证据。模拟情绪改善、依赖程度和对话时长不作为治疗效果或优化奖励。

### 5.3 证据评审

对最终回答提取专业声明，包括藏在安慰句里的健康判断。每条记录 `claim_text`、`citation_ids`、`source_quote`、`source_offsets`、`applicability`、`verdict` 与简短理由。

- 先用程序验证来源 ID、快照、原文片段和偏移，再由独立裁判判断支持关系；允许“支持、矛盾、依据不足、无法判断”。
- 独立报告声明支持率、引用覆盖、条件/例外保留、检索遗漏和误拒答。没有专业声明的陪伴回复记为不适用，不自动当作满分事实回答。
- 同时衡量应答问题覆盖率，防止优化器通过“全部拒答”获得高支持率。
- 区分忠于来源与现实正确：未经专业审核、过期或人群不适用的来源，不能因语义匹配就获得发布授权。
- 声明提取可能漏项，裁判也可能误判。高风险、争议和抽样合格案例都须有人工复核；模型一致不能取代审核真值。

### 5.4 校准与抗评分投机

先用约 30 段人工标注对话做裁判试验，再补足暴露出的场景缺口。目标用户参与自然度校准，专业人员负责健康内容与安全判断，分歧按维度处理。该规模仅适合初步校准，不作为稳定准确率估计。

- 从实际可用的不同模型家族中比较模拟器、裁判和反思模型，不根据通用排行榜直接指定“最强裁判”。
- 匿名候选身份，交换答案顺序；测试长度偏好、模型自偏好、过度拒答偏好与对评分指令注入的抵抗。
- 对话、证据和候选输出都作为不可信数据；裁判不执行其中“请给满分”等要求。要求短理由与可观察证据，不收集模型隐藏思维链。
- 记录与人工的一致性、关键风险漏检/误报及不确定率；不能仅用整体相关性掩盖某类风险漏判。
- 优化期间冻结裁判提示与版本；更换裁判后须重评基线，不能把评分器变化算作产品进步。
- 提示优化早期可单裁判筛选，入围候选增加另一模型家族的独立复评；争议不能简单平均掉。

## 6. 改进循环与发布门禁

### 6.1 先归因，后选择改进手段

| 失败类别 | 首选改进 | 审核边界 |
|---|---|---|
| 泛化安慰、说教、回应长度不合适 | 提示或少量示例候选 | 可进入 GEPA 提示搜索 |
| 错误意图、遗漏用户纠正 | 对照提示问题与状态/路由问题 | 状态或路由改动走代码审查，不能只补提示 |
| 库中无答案或来源质量差 | 内容补充、专业审核、快照更新 | 优化器不能生成医学真值或自行发布知识 |
| 库中有答案但未检索到 | 固定知识快照下对照检索策略 | 召回、支持率、误拒和成本共同验收 |
| 引用正确但结论外推 | 约束生成、声明验证或审核知识卡 | 不以“语气更好”抵消事实问题 |
| 固定倾听/风险话术循环、规则误伤 | 最小复现、规则或状态修复 | 单测、独立审查和完整回归后发布 |

### 6.2 有界优化

1. 建立当前版本基线，保存完整结果与分类失败样本。
2. 只向优化器开放优化集及允许修改的提示组件，返回“分数 + 文字反馈 + 可核验失败位置”。
3. 每轮只改变一类因素；第一批每轮最多 3 个提示候选，避免同时换模型、换知识库和改检索后无法归因。
4. 先执行确定性测试，再跑验证集与多轮安全回归；失败候选不进入发布候选池。
5. 入围候选做独立裁判复评、人工抽查和封存验收；保留基线结果，报告代价及退步场景。
6. 达到调用/费用/时间上限或连续没有可靠收益时停止。评测故障不算通过，不能只统计成功完成的请求。

本项目只使用 GEPA 的受控提示优化能力。代码改动通过正常分支与审查流程；禁止优化器编辑 `response_policy.py`、审核事实、评分规则或生产配置。安全边界可以经独立人工决策修订，但不得作为自动搜索的自由变量。

### 6.3 发布要求

- 确定性回归通过；关键安全案例无已知违规，争议风险必须审结。任一严重违规阻断发布，不能与自然度分数加权抵消。
- 自然度改善在固定条件重复实验中可见；事实支持、应答覆盖、偏好遵守和误拒答没有超出事先约定范围的退步。
- 实验开始前定义比较指标、允许退步范围及样本量计划。按场景家族汇总，报告样本数、重复波动及适用的置信区间，不能把同一场景的多次采样当独立用户。
- 封存集、小规模试验样本或零观察违规均不能证明临床零风险；证据不足时结论是“尚不确定”，不是继续调阈值直到通过。
- 知识变更完成专业审核，候选版本通过人工批准，能回退到明确版本；没有审核责任人或回滚方案则不得扩大试用范围。

首期流水线不自动部署，不自动修改线上模型，也不进行 RL、权重微调或在线探索。

## 7. 接入当前项目

先新增独立评测环境和运行器，不改写现有产品为一个绕开边界的通用聊天模块。以下目录是规划，不是已经存在的可执行系统：

```text
evals/
  scenarios/       # 版本化场景及集合清单
  rubrics/         # 陪伴、事实、安全、模拟器评分规则
  adapters/        # 现有助手和模型供应商适配器
  runner.py        # 有界多轮运行与故障记录
  graders.py       # 程序检查及模型评审
  optimize.py      # 获准提示候选的搜索
  report.py        # 基线对比、失败列表、预算和发布结论
```

- 快速逻辑实验调用现有 `app.answer()`，使用独立状态与固定知识快照；另做 HTTP 全链路测试，避免绕过会话持久化和发布出口。
- HTTP 适配器先 `GET /api/session` 获取 Cookie/revision，再用新 request_id 提交 `POST /api/ask`；这两个请求均须携带 `X-Requested-With: BabyAssistant`。只发送当前消息，不能注入客户端 history/state。
- 每个场景、候选和重复实验隔离会话；重试同一请求才复用 request_id。红队回溯需新会话重放有效前缀，不能把服务端状态当作可随意覆盖的客户端历史。
- 启动专用测试实例，隔离数据库、知识文件、端口和配置，不向用户正在使用的实例压测；服务端口以实际 `PORT` 配置为准。现有进程锁不能保护多个服务共用 SQLite。
- 首期用 JSONL、结构化报告与本地受控存储记录结果；需要协同复核和实验对比时接 Langfuse，不把自部署误认为零运维或自动合规。
- promptfoo 只补充多轮对抗测试，需配置有状态会话适配，不直接使用默认传完整历史的方式。
- GEPA/DSPy 等依赖放独立环境，实施时核对 Python 兼容性、版本、许可和实际 API，不为了评测先升级业务服务或引入多个主框架。

每个实验至少记录 `run_id`、场景/家族/集合、基线或候选版本、模型与参数、提示/裁判/知识版本、可见对话、最终答案、引用、状态变化、耗时、token/成本、评分依据、异常及人工结论。输入输出的具体保留范围按下一节约束；日志不包括 API Key、会话凭证或隐藏思维链。

## 8. 运行发现与人工处理

评测提高发布前发现率，运行监测负责新场景与分布变化。两者不能互相替代。以下为待建设流程，不表示目前已有值班或医疗响应服务。

| 角色 | 必须承担的责任 |
|---|---|
| 产品/评测负责人 | 检查反复出现的体验问题、裁判偏差与用户反馈，维护场景覆盖 |
| 技术维护者 | 监控上游失败、超时、输出拦截、状态冲突，确认告警并修复/回滚 |
| 专业内容审核者 | 审核健康资料、适用条件、风险类案例及争议结论 |
| 发布负责人 | 核对证据、未关闭问题、审核与回滚记录，决定是否扩大试用 |

内测前指定具体责任人、替补和响应时限；角色可兼任，但不能无人负责。异步人工复核不是紧急救助通道，也不能让急症响应等待裁判或工单处理。

处理链：发现 -> 分级 -> 通知 -> 人工确认认领 -> 影响评估 -> 停用受影响能力或回滚 -> 修复/内容审核 -> 新增回归 -> 复测关闭。记录检测耗时、认领耗时、未处理队列年龄、重复故障与回滚结果。

- 系统性危险专业输出或严重隐私问题按阻断级处理；普通话术问题与上游短暂故障分别排队，不用统一低分替代分级。
- 对运行错误记录必要元数据；内容评审使用经授权样本。高风险信号和用户投诉之外，保留随机抽检，避免只复核模型已经发现的问题。
- 用合成故障验证“会告警、有人收到、能够认领、回滚后有效”，包括超时、错误来源、输出阻断和队列失败。发现检测服务失效时也须产生运维告警，不能静默视为健康。
- 自部署 Langfuse 仍需访问控制、脱敏、保留期限和删除机制；进入第三方裁判的内容也受供应商数据政策约束。
- 默认不把完整健康对话复制到观测平台。原文进入复核/评测需授权、最小化和限期保存；授权撤回与删除应覆盖关联 trace、工单和派生评测样本，并说明备份及供应商保留边界。
- 用合成或充分脱敏且许可明确的样本做公开代码仓库中的回归数据；真实用户对话、凭证和私有评测原文不入 Git。

## 9. 分阶段实施、预算与交付物

| 阶段 | 交付 | 退出条件 |
|---|---|---|
| E0 校准与接线 | 场景契约、首批约20场景、约30段人工裁判校准样本、独立运行器 | 能复现对话、识别评测失败、估算成本；裁判已暴露的重大误判得到处理 |
| E1 基线与覆盖 | 扩展约60场景，固定历史/自适应/长对话测试，分类基线报告 | 能指出具体失败轮次和来源，区分内容、检索、状态、生成、裁判问题 |
| E2 第一轮改进 | 最多3个提示候选或一项独立检索实验，独立验证、人工复评 | 改进有证据且没有不可接受退步；无收益也应形成明确结论 |
| E3 发布与运营 | 封存验收、责任人与时限、告警/回滚演练、受控试用计划 | 不以评测系统代替内容审核、隐私保护或产品上线门禁 |

工程粗估：模型接口和人工审核可用的前提下，1–2 周争取完成可复现基线和一轮受控改进，不包含完整上线或证明收益的时间承诺。专业审核和目标用户招募不足时，必须明确标记验证缺口。

预算按实际调用核算：场景数 × 平均轮数 × 重复次数 × 候选版本数决定助手响应次数；每轮还可能有模拟器、planner、生成器调用，另外计算声明提取、裁判与反思开销。比如 20 场景 × 6 轮 × 2 版本即 240 次助手响应，不是总 API 调用数。

每次启动前配置调用数、token、金额、时间、最大轮次和并发上限。先小样本估算，再批准扩展；长上下文和多裁判不能按单轮成本外推。缓存键绑定模型/提示/知识/输入版本，重复性实验中禁止用缓存把多次运行伪装成独立样本。

首批报告必须包含：运行清单、各维度指标及适用样本数、失败复现、裁判与人工分歧、无效轨迹及上游错误、版本对比、成本、未知项、是否推荐发布和签核人。未来再根据真实失败分布决定是否需要微调、更多模型或更复杂检索。
